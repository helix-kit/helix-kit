# Build-time page gating for static-export edge UIs

**Experiment.** Can we make the *enabled feature set* a build-time input to a
Next.js static export, so that features a given device doesn't run — **and their
heavy npm dependencies** — never make it into the shipped `out/` bundle?

Context: a prior production system (and Helix's edge UI) ship the device console
as a single static-export zip (`output: 'export'` → `out/` → `device-ui.zip`, served
by the Go `cloud-comm` static server). Today every route folder present on disk
is discovered by the bundler, so a device that runs 4 of 50 features still ships
the workflow editor (`@xyflow/react`), charting (`recharts`), the dashboard grid
(`react-grid-layout`), etc. There is no page-level dead-code elimination — every
feature is a **static import** wired through a **hardcoded nav array**.

This lab reproduces that shape with a minimal app (5 features: 2 light, 3 each
pulling a distinct heavy dep) and proves out two gating strategies with real
`next build` measurements.

## The core mechanism

Next.js builds its module graph starting from the **route files it finds on the
filesystem**. A route that isn't on disk is never an entrypoint, so nothing it
imports enters the graph, so its dependencies are never bundled and never
tree-shake-surviving. That single fact is the whole lever: **make route presence
a function of the enabled feature set.**

## Layout

```
app/                         a real Next.js static-export app
  src/features/<id>/
    feature.json             { id, route, label, heavy, deps }  ← the manifest
    page.tsx                 thin route entry: renders ./impl
    impl.tsx                 the actual feature (heavy ones import the fat dep)
  src/app/page.tsx           landing; renders the GENERATED nav registry
  src/app/(gen)/             generated by gate.mjs — Approach A route folders
  src/app/(all)/             generated by gate.mjs — Approach B route folders
  src/generated/nav.ts       generated by gate.mjs — enabled-only nav registry
profiles.json                named enabled-feature sets (full, minimal, …)
gate.mjs                     prepare the app for a profile, then next build
measure.mjs                  build a matrix of profiles, tabulate out/ size + deps
```

Features are self-contained modules that live **outside** `app/`. Nothing is a
route until `gate.mjs` materializes it. The app shell imports only the generated
`nav.ts` (plain data — route + label strings), so it never pulls feature code.

## The two approaches

### Approach A — manifest-driven filesystem route assembly (recommended)

`gate.mjs --approach filesystem` reads the enabled list, then for each enabled
feature writes a one-line re-export route into `src/app/(gen)/<route>/page.tsx`
(`export { default } from '@/features/<id>/page'`) and regenerates `nav.ts`.
Disabled features get no route file at all.

- Disabled feature ⇒ no entrypoint ⇒ route, code, **and deps all absent** from `out/`.
- The gated route returns **404** — it doesn't exist.
- **Bundler-agnostic**: pure filesystem, works identically under webpack or Turbopack.
- `next.config` does nothing special.

### Approach B — webpack module-replacement stubbing

`gate.mjs --approach stubbing` keeps **all** routes on disk (`src/app/(all)/`) and
passes `HELIX_GATED_OUT=<disabled ids>` to the build. `next.config.mjs` uses
webpack's `NormalModuleReplacementPlugin` to swap each disabled feature's `./impl`
module for an empty stub, so its heavy deps leave the graph and tree-shake out.

- Heavy deps **are** removed (same as A), but the **route still exists** and emits
  a small dead HTML page; nav must hide it at runtime.
- **Bundler-coupled**: relies on webpack. Under Next 16 / Turbopack you'd port
  this to `turbopack.resolveAlias`.
- More machinery for a strictly weaker result than A.

## Results (measured, `next build` static export)

`node measure.mjs --approach filesystem` — client-JS size of `out/` and whether
each heavy dep's signature survives in the emitted chunks:

| profile | total | client JS | chunks | xyflow | recharts | grid |
| --- | --- | --- | --- | --- | --- | --- |
| full | 1490 KB | 1383 KB | 23 | IN | IN | IN |
| minimal | 811 KB | 767 KB | 16 | — | — | — |
| workflow-only | 1009 KB | 931 KB | 19 | IN | — | — |
| charts-only | 1200 KB | 1144 KB | 18 | — | IN | — |
| no-workflow | 1291 KB | 1218 KB | 20 | — | IN | IN |

The dep columns track the enabled set **exactly**. `minimal` (2 light features)
ships **767 KB vs 1383 KB** client JS — a ~45% cut — with all three heavy deps
provably gone. `workflow-only` keeps xyflow and drops the rest; `no-workflow`
drops xyflow and keeps the rest. No leakage.

Approach B (`--approach stubbing`) removes the same dep weight (client JS within
~1 KB of A) but every profile is a few KB larger and carries extra chunks because
it still emits the dead gated routes — e.g. `minimal` is 846 KB total / 19 chunks
vs A's 811 KB / 16 chunks, and `/workflows/` still serves a 277 B stub page
instead of 404.

## Reproduce

```sh
cd app && npm install && cd ..
node gate.mjs --profile minimal --build       # one build
node measure.mjs                               # full matrix, filesystem
node measure.mjs --approach stubbing           # full matrix, stubbing
# ad-hoc feature set:
node gate.mjs --features overview,workflow --build
```

Results land in `results/` (`matrix-*.json`, `summary-*.md`).

## What this does and doesn't remove

Both approaches remove the dep from the **shipped bundle** (`out/`), which is the
thing that ends up on the device. Neither uninstalls the package from
`node_modules` — xyflow is still present at *build* time (it's just never
imported into an enabled graph). For the device artifact that's irrelevant: the
zip only contains `out/`.

If you also want to prune the **install graph** (don't even `npm install` xyflow
when no enabled feature needs it — faster, smaller CI builds), that's a natural
evolution of Approach A, sketched below.

### The framework floor, and how to minimize it

Everything above removes *marginal* feature weight but leaves a fixed **framework
floor**: even the 2-light-feature `minimal` build is ~767 KB raw / ~102 KB gzip,
almost all of it React + the Next.js App Router client runtime (only ~9 KB is app
code). Gating can't shrink that floor — it's the price of Next App Router.

The [`minimal-floor/`](minimal-floor/) sub-experiment attacks the floor itself by
dropping Next for a static Vite SPA and swapping React for Preact/compat, keeping
the same gating and the same feature components (reused verbatim). Result: the
minimal floor drops from ~102 KB gzip (Next) → 58 KB (Vite+React) → **8.4 KB
(Vite+Preact)**, ~12× smaller, with all three heavy libs (xyflow/recharts/grid)
verified working under Preact. See `minimal-floor/README.md`.

## Recommended direction for Helix

**Adopt Approach A**, evolved along the grain of the existing architecture:

1. **Feature manifest is the source of truth.** Each feature already maps cleanly
   to a `@app/*-ui` / `@helix-hq/*` workspace package. Give each a manifest
   (`route`, `label`, `deps`, `nav group`, `requiresComponents`). The device's
   enabled set (which already exists conceptually — `services.json`
   `local.defaultEnabled`, `requiresComponents`) selects features.
2. **Codegen the routes + nav from the manifest** at build time (what `gate.mjs`
   does here), replacing the hand-maintained `NAV_ITEMS` array in
   `edge-app-shell.tsx`. Nav and routing then can't drift from what's actually
   built.
3. **Bundler-agnostic** means it survives the device console's `--turbopack` build
   unchanged — no webpack coupling.
4. **Install-graph pruning (optional next step):** because features are workspace
   packages, generate the device app's `dependencies` from the enabled manifest
   so `pnpm install --filter` only pulls enabled features' deps. This is the only
   way to get heavy packages out of `node_modules` too; it builds directly on the
   manifest from step 1.

### Caveat surfaced by the investigation

A dep is only removed if **every** enabled feature stops importing it. In one
such app, `@xyflow/react` is imported by both a workflow editor and several other
features. Gating out
"Workflows" alone would not drop xyflow while any of those stay enabled. The
manifest's `deps` must reflect *all* co-consumers, and the win is largest for
deps with a single feature owner. This is a data-modeling requirement, not a
limitation of the mechanism.
