# Helix Communication Protocol V1

Helix is a new protocol and framework for typed UI-to-device communication.

## Goals

- Keep the core wire packet small and transport-neutral.
- Keep gateway routing, auth, device IDs, MQTT topics, and browser connection
  ownership outside the protocol packet.
- Let service contracts be easy to write by hand, with code generation as an
  optional convenience.
- Use the same communication model for direct device links, BLE, WebSocket,
  MQTT, Serial, and user-defined gateways.
- Support TypeScript, Python, Go, and C++ consumers as independent installable
  packages.

## Protocol Layers

Helix is split into small layers that can be installed independently.

### Core Protocol

The core protocol only defines the packet shape, request correlation, encoding,
decoding, and timeout handling. It does not know about services, methods,
devices, transports, gateways, or auth.

```ts
type HelixPacket<TMessage = unknown> = {
  requestId?: string;
  message: TMessage;
};
```

`requestId` is generated by the caller runtime when a response is expected. It
is protocol metadata and must not be part of a method payload.

### Service/Method Protocol

The service protocol sits over the core packet and defines the message carried
inside `packet.message`.

```ts
type HelixMessage<TPayload = unknown> = {
  service: string;
  method: string;
  payload?: TPayload;
};
```

The device service broker dispatches by `message.service` and `message.method`.
Clients subscribe by matching the same fields.

### Transport Providers

Transport providers move `HelixPacket` values over a concrete medium:

- WebSocket
- MQTT
- BLE
- Serial
- custom user transports

Transports may have their own connection state and framing rules, but that state
is not part of the Helix packet.

### Gateway

Gateway state is connection context, not protocol data.

1. A client connects to a gateway using a connection string.
2. The connection string includes auth material and target `deviceId`.
3. The gateway validates the connection and stores `{ connection, authContext,
   deviceId }`.
4. When the client sends a Helix packet, the gateway already knows the target
   device from the connection context.
5. The gateway forwards the packet to that device using its own transport
   details, such as MQTT topics.

`deviceId`, session owner maps, MQTT topics, and auth checks are gateway
implementation details. They must not be sent by client callers per request.

## Packet Examples

### Request

```json
{
  "requestId": "req-123",
  "message": {
    "service": "gpio-control",
    "method": "set-gpio",
    "payload": {
      "pin": 2,
      "high": true
    }
  }
}
```

### Response

```json
{
  "requestId": "req-123",
  "message": {
    "service": "gpio-control",
    "method": "gpio-control-state",
    "payload": {
      "pins": [{ "pin": 2, "level": 1 }]
    }
  }
}
```

### Async Device Message

```json
{
  "message": {
    "service": "live-feed",
    "method": "sdp-answer",
    "payload": {
      "sessionId": "live-session-1",
      "sdp": "..."
    }
  }
}
```

The protocol does not filter async messages. If a live-feed payload contains a
session ID, client app code decides whether to use or ignore it.

## Request And Subscription Semantics

- `request()` creates a `requestId`, sends `{ requestId, message }`, and waits
  for a packet with the same `requestId`.
- Responses are correlated only by `requestId`.
- Method payload contracts must not include `requestId`.
- `subscribe()` listens for messages by `service` and `method`.
- Device-originated async communication is just a message without `requestId`.
- There is no separate wire-level distinction between event and notify.

Product lifecycle events that are stored in a database are a different product
surface and are out of scope for this communication protocol.

## Contract Authoring

Contracts should be simple enough to write manually. Code generation should use
the same public API that a human developer would use.

Recommended TypeScript shape:

```ts
import { z } from 'zod';
import { defineServiceContract, method, message } from '@helix/protocol-service';

const SetGpioInput = z.object({
  pin: z.number().int(),
  high: z.boolean(),
});

const GpioState = z.object({
  pins: z.array(
    z.object({
      pin: z.number().int(),
      level: z.number().int(),
    }),
  ),
});

const GpioError = z.object({
  error: z.string(),
});

export const gpioControl = defineServiceContract({
  service: 'gpio-control',
  methods: {
    setGpio: method({
      name: 'set-gpio',
      input: SetGpioInput,
      output: GpioState,
      error: GpioError,
    }),
    readGpio: method({
      name: 'read-gpio',
      input: z.object({}),
      output: GpioState,
      error: GpioError,
    }),
  },
  messages: {
    stateChanged: message({
      name: 'gpio-control-state-changed',
      payload: GpioState,
    }),
  },
});
```

## Package Model

TypeScript packages:

- `@helix/protocol-core`
- `@helix/protocol-service`
- transport packages such as `@helix/transport-ble`
- `@helix/gateway`

Python packages:

- `helix-protocol-core`
- `helix-protocol-service`
- transport packages
- gateway package

Go modules:

- `github.com/helix/protocol/go/core`
- `github.com/helix/protocol/go/service`

C++ packages:

- `helix_protocol_core`
- `helix_protocol_service`

## Code Generation

Code generation is optional. Generated code should be readable and use the same
contract API as hand-authored code.

The uv/click command surface is:

```bash
helix protocol validate --source <path>
helix protocol generate --source <path> --target typescript --out <dir>
helix protocol generate --source <path> --target python --out <dir>
helix protocol generate --source <path> --target go --out <dir>
helix protocol generate --source <path> --target cpp --out <dir>
```

Contracts and generated code are **co-located with the real service**: the JSON
lives beside the implementation (e.g.
`linux/device/go/internal/shell/contracts/shell.json`) and each target writes
next to its consumer via `helix.contracts.json` + `helix protocol generate-all`.
A single JSON is the source of truth across languages.

Each method names its request `input`, response `output`, and `error` schemas,
plus an optional `outputName` — the response method name a device replies with
(`open` → `opened`, `ping` → `pong`) when it differs from the request. The
generators emit:

- **Go** (`--target go`, `package generated`) — a struct per schema (JSON tags,
  `,omitempty` for optionals), `Parse<T>` decoders, a `<Svc>Handler` interface
  (`Handle<Method>(ctx, req) (out, error)`), and a `Dispatch<Svc>(...)` that
  decodes the payload, calls the typed handler, and replies via
  `ipcutil.Respond`/`RespondError` under the declared response method name.
- **Python** (`--target python`) — a frozen `@dataclass` per schema (with
  `wire_name` metadata for snake⇄camel mapping via the emitted `_runtime.py`), a
  `<Svc>Handler` `Protocol`, and a `dispatch_<svc>(...)` mirroring the Go shape.

The device services (`echo`, `shell`, `port-forward`) implement only the typed
handler; all wire decoding, the method switch, and response naming come from the
generated code.

## Validation Expectations

- Concurrent requests route by `requestId`.
- Method payloads do not contain protocol metadata.
- Async messages are delivered through the same message shape.
- Gateway `deviceId` is connection context, not packet data.
- Transport implementations preserve the Helix packet shape end to end.
